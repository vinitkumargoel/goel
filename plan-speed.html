2 · How the engine works today

Verified by reading SegmentedTransfer.swift (1,435 lines), HTTPEngine.swift, curl_bridge.c, torrent_bridge.cpp and the full settings→engine config chain.

The HTTP pipeline

  1. Probe — cheap HEAD; falls through to a 1-byte ranged GET unless range support is already proven, so servers that only advertise Accept-Ranges on GET still segment (HTTPEngine+Probe.swift:121–160). Extracts size, ETag/Last-Modified, filename, and published digests (RFC 3230 / RFC 9530 / Content-MD5 + .sha256 sidecar).
  2. Plan — segment count from the traffic profile + cross-download ConnectionBudget (per-host and global caps, 64 KiB min segment; ConnectionBudget.swift:62–74). With ≥2 bound adapters, multiPathSegmentCount overrides it: adapters × streams-per-adapter, hard cap 32 (NetworkAdapter.swift:207–226).
  3. Split — makeRanges cuts N equal ranges once (SegmentedTransfer.swift:739–751). The layout is frozen for the download's life and serialized into the resume cursor.
  4. Pump — per segment: URLSession data task with a delegate-driven ChunkStreamer (real TCP backpressure via suspend/resume at 8 MiB/2 MiB watermarks — good engineering), or the curl-based BoundHTTPClient when interface-bound. 64 KiB flushes into a preallocated sparse file, each flush hopping to a Ledger actor.
  5. Adapt — a per-download ConnectionGovernor shrinks fan-out on 429 (monotonic — it never grows back; ConnectionGovernor.swift:85–87). A MirrorPool round-robins mirrors and demotes misbehaving ones.
  6. Verify — every 206's Content-Range total must match; whole-file byte accounting before .completed; optional checksum verification.

What is already genuinely good

  • solid Delegate-based chunk streaming with true TCP backpressure (replaced byte-per-await AsyncBytes)
  • solid Resume cursors validated by ETag/Last-Modified and on-disk preallocation check — no silent corruption paths
  • solid Cross-host redirect/mirror secret-stripping and SSRF refusal in RedirectSanitizer
  • solid Aggregate rate-limiter chain that holds the cap in sum across downloads
  • solid Cancellation correctness in the governor (no doomed requests after teardown)
  • solid Overflow-safe range math against hostile Content-Length

The gap is not correctness. It is that the engine's throughput policy — how many bytes to keep in flight, where, and for how long — was set conservatively and statically, while the state of the art is adaptive everywhere.

3 · The seven ceilings on HTTP throughput

Each with evidence, the state-of-the-art comparison, and the fix.

ceiling 1  The default profile caps everyone at ~420 Mbps

TrafficProfile.swift:73 · HTTPEngine.swift:155 (shared pacer) · torrent_bridge.cpp:180 (same cap → libtorrent)

"Medium" is the default profile and sets maxDownloadBytesPerSec = 50 MiB/s, enforced by the engine-wide downloadPacer across all downloads in sum — and pushed into libtorrent as download_rate_limit. Every user on a ≥500 Mbps line runs at half speed or less without knowing why. The comment in the file shows this was already raised once (10 → 50 MiB/s) for exactly this reason; the same logic now applies again at gigabit+.

Fix: default the byte cap to unlimited (keep connection caps as the safety valve — that's what they're for), or run a 3-second first-launch calibration and set the cap to 110% of measured line rate. Keep "Low" as the true limiter. One-line change; the single largest win for users on defaults.

ceiling 2  Static segmentation — the tail collapse

SegmentedTransfer.swift:92–99 (ranges frozen in init) · :739–751 (equal split, never revisited)

Ranges are cut into N equal pieces at start. When a fast segment finishes, its connection closes; the download ends at the pace of whichever segments were unlucky — slow CDN edge, lossy path, throttled mirror, slower NIC. With aggregation on, round-robin adapter assignment makes this structural: a 1 Gbps Ethernet segment finishes early and sits idle while a 100 Mbps Wi-Fi segment grinds through the same-sized range.

static
 
 
stealing
 
 
Hatched = connection idle while the download is still running. Static: finish time = slowest segment. Stealing: freed connections bisect the largest remaining gap; all N stay busy to ~100%.

State of the art: IDM documents the exact rule — when a connection frees, find the largest remaining segment and divide it in half, reusing the hot connection "without additional connect/login stages." aria2's picker hands a finishing connection the byte range adjacent to its position (same socket, zero handshakes) and only bisects when no adjacent work exists.

Fix: replace the fixed [Range64] with a shared range ledger: on segment completion, (a) try the adjacent unclaimed gap on the same connection via a new Range request; (b) else bisect the largest remaining gap (floor: max(4 MiB, per-connection rate × 3 s)); (c) stall detector (<N KB/s for 10 s) kills and re-steals. The resume-cursor format already stores arbitrary ranges + completed counts, so persistence barely changes.

ceiling 3  Multi-path curl: a handshake per segment and a 16 KB buffer

curl_bridge.c:479–480 (FRESH_CONNECT + FORBID_REUSE) · :432/:514 (easy handle per attempt) · no CURLOPT_BUFFERSIZE set · BoundHTTPClient.swift:103 (thread per request)

Every interface-bound range request builds a fresh curl easy handle, forbids connection reuse, performs a full TCP + TLS handshake, restarts TCP slow-start from zero, and delivers the body in 16 KB callbacks — each of which is a separate FileHandle.write syscall (BoundHTTPClient.swift:188). curl's own docs cap CURLOPT_BUFFERSIZE at 10 MB; users have measured order-of-magnitude callback-overhead differences at high rates.

Fix: one long-lived curl multi (or at minimum a per-adapter easy-handle pool) with connection cache + shared TLS session store (CURLSH); CURLOPT_BUFFERSIZE 512 KB–2 MB; coalesce writes to ≥1 MiB. This is also the prerequisite that makes work-stealing cheap on the bound path — re-splits become one Range request on a warm connection, exactly IDM's trick.

ceiling 4  HTTP/2 coalescing quietly serializes your "parallel" segments

URLSession path (default protocol negotiation) · curl_bridge.c:467 (CURL_HTTP_VERSION_2TLS)

URLSession multiplexes all data tasks to an h2 origin onto one TCP connection. Eight "segments" against an HTTP/2 CDN can mean eight streams sharing a single congestion window — the parallel-TCP speedup (N independent congestion controllers) silently evaporates, and one lost packet head-of-line-blocks all eight. This is a well-documented failure mode (e.g. .NET saw h2 downloads at a fraction of HTTP/1.1 speed for large bodies).

Fix: fetch segments over HTTP/1.1 — separate connections, separate cwnds (curl path: CURL_HTTP_VERSION_1_1 for ranged segment GETs; URLSession offers no h2 opt-out, which argues for routing all segmented traffic through the curl engine once ceiling 3 is fixed). Keep h2/h3 for probes and single-stream bodies.

ceiling 5  The governor only ratchets down

ConnectionGovernor.swift:85–87 · design note :17–23

One transient 429 burst (a CDN edge hiccup, a shared rate-limit window) permanently halves the fan-out for the rest of a multi-hour download. The code comments acknowledge re-probing belongs to "a future, slower control loop" — that loop is exactly what the state of the art runs (AIMD: probe +1 slot after a clean multi-minute window; back off again on 429).

Fix: add the slow loop: after T seconds with zero 429s and all segments healthy, raise the ceiling by 1 toward the original request. Trivially safe — worst case is one extra 429 per probe interval.

ceiling 6  64 KiB flushes: a syscall + actor hop every 64 KiB

HTTPEngine.swift:93 (flushSize = 64 * 1024) · SegmentedTransfer.swift:702–724 (pump loop)

At 1 GB/s aggregate this is ~16,000 write syscalls and ~16,000 Ledger actor hops per second, plus a rate-limiter hop each when capped. Fine at 100 Mbps; measurable CPU at multi-Gbps.

Fix: raise flush to 1–4 MiB (adaptive: min(4 MiB, rate/8)), advance the ledger per flush as today, and write via pwrite on one shared fd. aria2 ships a 16 MiB coalescing cache for the same reason. Progress granularity stays sub-second at any speed that notices the change.

ceiling 7  Single-connection downloads leave everything on the table

SegmentedTransfer.swift:114–122 (first-adapter pin) · :541 (truncate on entry) · :591–593 (no resume) · macOS net.inet.tcp.autorcvbufmax = 4 MiB

Covered in depth in §4 — this is your reported aggregation bottleneck. Also note the OS-level ceiling: macOS caps auto-tuned receive windows at 4 MiB, which caps any single TCP flow at ~1 Gbps at 33 ms RTT (~330 Mbps at 100 ms). Segmentation is the workaround when the server allows it; when it doesn't, honesty + failover is the play.

4 · Network aggregation and the single-connection case

Diagnosis of "aggregation does nothing when there's only one connection" — what's a bug, what's physics, and the fix ladder for each.

What actually happens today

Aggregation binds different TCP connections to different NICs. That requires ≥2 connections, which requires the server to support ranges with a known size (canSegment, HTTPEngine.swift:488). When it doesn't:

  • The transfer silently collapses to a single stream on boundAdapters.first — the first NIC in the list, not the fastest (SegmentedTransfer.swift:118–119). Your second ISP sits idle.
  • That path truncates the destination file on every entry (:541) and cannot resume (:591–593) — a retry after 1.9 GB of a 2 GB unranged download restarts from zero and destroys the partial.
  • No signal reaches the UI: the "why am I on one path?" reasons (.noRanges, .serverRejected…) are defined but never produced anywhere (NetworkAdapter.swift:101–104).
  • Bonus finding: on the bound path, pause discards all in-flight segment bytes from the resume cursor (abort returns without crediting bytesWritten, SegmentedTransfer.swift:401–404) and progress only ticks at segment boundaries (no onBytes wired at :397–399) — so multi-path downloads show staircase progress and re-fetch data after pause.

What is physics, what is fixable

A single TCP flow cannot be striped across two interfaces client-side — packets of one 5-tuple follow one route. True single-flow bonding requires MPTCP on both ends (virtually no public HTTP servers speak it; on macOS it's client-only via Network.framework, and URLSession's multipathServiceType is iOS-only with the aggregate mode entitlement-gated) or a bonding relay (the Speedify model — packets tunneled across all links to a server you operate, which reassembles the flow). Everything else is engineering you can ship now:

Manufacturing more connections when the server "gives one"

"One connection" is four different situations, each with its own unlock. The decisive insight: most per-client limits are per IP address — and a machine with two ISPs has two public IPs. Aggregation shouldn't just spread connections; it should multiply the allowance.

shipped Rows 1 and 3 are implemented on branch feat/single-conn-aggregation: the mid-flight upgrade (background ranged re-probe → abort the stream → keep the prefix → re-enter segmented across all NICs) and per-source-IP connection budgets (one ConnectionGovernor per adapter, so a 429 on one ISP shrinks only that path's ceiling), plus a mid-flight channel to charge the extra connections against the cross-download budget. Rows 2, 4, 5 and 6 remain proposals.

Account-level (login-based) limits do not multiply across IPs. Always honor 429/Retry-After — the goal is using independent allowances, not hammering one.

Structural fixes in the bridge

  • Stop polling with all-flags status(). Every second, per torrent, the bridge requests every status field — including an O(pieces × peers) availability walk — executed on libtorrent's network thread, the same thread moving peer traffic (torrent_bridge.cpp:369, TorrentEngine.swift:465–575). Pass only the ~10 flags actually read; better, switch to post_torrent_updates() + state_update_alert — one batched, non-blocking update per tick for all torrents.
  • Make resume-saves async. gt_save_resume_data blocks the engine actor up to 2 s and its alert-drain loop swallows other torrents' alerts, causing cascading save timeouts (torrent_bridge.cpp:292–311). Route through a single alert dispatcher.
  • Subscribe performance_warning alerts — libtorrent literally tells you when it's disk- or buffer-bound; today nothing listens (torrent_bridge.cpp:140–142).
  • Plan the libtorrent 2.1 upgrade (July 2026): default pread_disk_io backend (fixes mmap's giant-RSS complaints on macOS), hash-before-flush uploads, and WebTorrent peers on by default.
  • Adopt set_piece_deadline for the streaming/preview path — it's libtorrent's time-critical picker (queue-time-sorted peers, escalating busy-requests) and strictly better than plain sequential_download for "play while downloading."
  • Web seeds (BEP 19): expose add_url_seed — Goel° already has HTTP mirrors as a concept; a torrent with an HTTP source downloads at CDN speed with a swarm of zero. Raise max_web_seed_connections (3 → 8) and keep urlseed_max_request_bytes at 16 MiB so ranges coalesce.
  • Sandbox check: ensure the com.apple.security.network.server entitlement is present — without it there are no incoming peers and DHT/uTP degrade; that's a permanently firewalled client.

Expected effect: ramp-to-saturation drops from tens of seconds to single digits on healthy swarms (announce-all + connect boost + warm DHT + resume peers), sustained +20–50% on fast swarms (prefer_tcp, queue depth, disk queue, upload unclamp), rechecks ~cores× faster.

6 · State of the art — the reference points

What the fastest tools actually do, with the numbers that matter.

HTTP

  • IDM — dynamic "in-half division": largest remaining segment bisects when a connection frees; freed connections reused with zero reconnect/login; default 8, max 32 connections; stalled ranges reassigned to fast connections.
  • aria2 — 1 MiB pieces, adjacent-piece continuation on the same socket ("establishing connection is an expensive operation"), --min-split-size floor (never split below 2×), mirror selection by measured speed (feedback/adaptive), persisted per-server profiles. Unmaintained since Nov 2023 — there is a market vacuum here.
  • Parallel-TCP research — throughput scales near-linearly with stream count on lossy WANs until self-congestion; 4–8 streams captures most of the gain on clean paths (Hacker & Athey IPDPS'02; ESnet).
  • curl 2024–26 — CURLOPT_BUFFERSIZE up to 10 MB; TLS 1.3 early-data; HTTP/3 via ngtcp2 stable with 200 ms QUIC-vs-TCP eyeball racing; --mptcp (Linux). QUIC is CPU-bound above ~10 Gbps — H3 wins on lossy paths, not raw rate.
  • Multi-source standards — Metalink RFC 5854 + RFC 6249 (Link: rel=duplicate + mandatory Digest), RFC 9530 Repr-Digest — Goel° already parses digests; mirrors + work-stealing + per-edge-IP fan-out (CURLOPT_RESOLVE across all A/AAAA records) compose into one pool.
  • macOS — autorcvbufmax 4 MiB caps one flow at ~1 Gbps @ 33 ms; explicit SO_RCVBUF disables autotuning; parallelism is the sanctioned workaround.

BitTorrent

  • high_performance_seed() — the author's answer key: prefer_tcp, request queue 1500, connection_speed 500, send watermark 3 MiB, queued disk 7 MiB, timeouts 10/20/20 s, failcount 1, aio 8, checking_mem 2048.
  • qBittorrent — ships announce-to-all-trackers and -tiers, prefer_tcp, coalesced I/O, file pool 5000, 50 parallel HTTP announces; seedbox racing configs layer ConnectionSpeed 500 + BBR kernel tuning on top.
  • Piece picking — rarest-first + tit-for-tat is provably near-optimal for bulk (Legout IMC'06; Bharambe INFOCOM'06): don't reinvent it, tune around it. For streaming, set_piece_deadline's queue-time scheduler with escalating busy-requests is the modern answer (TorrServer's architecture, but native).
  • BitTorrent v2 — integrity/latency win (per-16 KiB-block attribution, instant bad-peer bans), not a throughput win; ship hybrid support, expect nothing from it on speed.
  • libtorrent 2.1 (Jul 2026) — pread backend default, WebTorrent on by default: browser peers become reachable swarm members.

8 · Benchmark harness — turning "50% → 100%" into a number

You can't tune what you don't measure. This is a one-week build that makes every optimization above provable.

HTTP matrix

  • Server: local nginx/caddy in Docker serving 100 MB / 2 GB / 10 GB files, with dnctl/pfctl (macOS) shaping profiles: RTT 20/80/200 ms × loss 0/0.5/2% × per-connection throttle on/off.
  • Baselines: curl -O (single stream), aria2c -x16 -k1M, Goel° current, Goel° after each fix.
  • Metrics: mean throughput, tail time (90% → 100% wall-clock — the work-stealing metric), time-to-first-byte, CPU-seconds per GB, bytes wasted on pause/resume.
  • Acceptance: ≥90% of line rate on 1 Gbps @ 20 ms/0% with 8 connections; tail time ≤ 10% of total; pause/resume waste ≈ 0; single-stream within 5% of curl.

Torrent matrix

  • Swarm-in-a-box: 10 dockerized libtorrent seeds, each capped at 20 MB/s, private tracker container; a 4 GB test torrent.
  • Metrics: time-to-first-piece, time-to-90%-of-line-rate (ramp), sustained throughput, recheck time for the 4 GB payload.
  • Acceptance: ramp ≤ 5 s warm / ≤ 10 s cold; sustained ≥ 90% of aggregate seed capacity; recheck scales with cores.

Aggregation matrix

  • Two shaped interfaces (e.g. 300 + 700 Mbps): assert aggregate ≥ 90% of the 1 Gbps sum on ranged downloads, correct fastest-NIC selection on unranged, and failover under mid-stream NIC kill with zero corrupted files.
