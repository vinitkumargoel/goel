Convert & Extract Audio: what's missing, and what I want to build

The feature works — it produces correct files. What it does not do is tell you anything while it works, or let you stop it. This page is the gap analysis and the proposed design, for you to approve or redirect before I touch any Swift.

The core problem is architectural, not cosmetic

A conversion has no object representing it. convertFile spawns a detached Task, drops the handle, and shows a 2.4-second toast. Nothing in the app holds a reference to the running job — so there is nothing to draw a progress bar from and nothing to cancel. Adding a spinner is not the fix; the job needs to exist first.

✓

Built — and four things in here changed on the way

This document was the plan. It has been kept as written and annotated where the implementation disagreed with it, rather than quietly edited to match. The four differences, each marked changed or not shipped where it appears:

  • Per-format size estimates in the Extract Audio menu are cut. They needed a probe process spawned from inside a submenu, and were wrong on the first right-click by design. The estimate survives where it can act — the free-space pre-flight.
  • No AVAsset fast path. It cannot open MKV or WebM, and cannot answer the codec half of the probe. One uniform ffmpeg -i covers every container.
  • Notifications follow the user's existing settings rather than a hardcoded “only when not frontmost”.
  • Recording conversions in History is not built. It was listed as lowest priority and droppable; it was dropped.

What happens today

Here is the complete user-visible life of a conversion, as the code currently writes it. The right column is what I'm proposing instead.

Today

  • 0.0sYou click Convert To → MKV.
  • 0.0sToast: “Converting to MKV…”.
  • 2.4sToast disappears. The app now looks idle.
  • 2.4s+No spinner, no bar, no row, no menu-bar hint, no Dock badge. Nothing.
  • …You cannot cancel. You cannot tell if it's running, wedged, or already finished.
  • …You right-click and hit Convert again, because there was no feedback. Now two ffmpegs run.
  • 6m 40sToast: “Saved ‘clip.mkv’”. If you were in another app, you never see it.
  • —On failure: 200 chars of ffmpeg stderr, in a toast, for 2.4 seconds. Uncopyable.

Proposed

  • 0.0sClick Convert To → MKV.
  • 0.1sA job card docks bottom-right and stays until you dismiss it.
  • 0.3sDuration probed → real percentage, not a spinner.
  • 1s+Bar advances. “38% · 4:12 of 11:02 · ~2m 30s left · 1.8×”.
  • any✕ cancels — SIGTERM, then SIGKILL, partial output deleted.
  • anySidebar shows “Media jobs 1”. Dock icon shows combined progress.
  • on stallCard turns amber: “No progress for 5 min — ffmpeg may be stuck.”
  • doneCard turns green with Reveal in Finder; notification if backgrounded.
  • on failCard turns red and stays, with full ffmpeg output + Copy.

Proposed design

One new owner object, one new view, and a rewrite of the process plumbing to stream progress. Parsing stays pure and lives in GoelCore — matching the rule this codebase already states out loud: “parsers live in GoelCore as pure functions while GoelApp owns the process plumbing”. That's what makes it testable without ffmpeg on CI.

The job model

// GoelApp/MediaJobCenter.swift — new
struct MediaJob: Identifiable {
    let id: UUID
    let input: URL
    let kind: Kind              // .convert(ext) | .extractAudio(format)
    var state: State            // .queued .probing .running .cancelling
                                // .finished(URL) .failed(String) .cancelled
    var fraction: Double?       // nil ⇒ indeterminate, and we SAY so
    var processedSeconds: Double
    var totalSeconds: Double?    // from AVAsset, else ffmpeg's -i banner
    var speed: Double?          // ffmpeg "speed=1.8x"
    var bytesWritten: Int64
    var lastAdvance: Date       // drives the stall detector
    var log: String             // full stderr, kept for the error card
}

// Owner. @MainActor + ObservableObject, matching AppViewModel's style.
final class MediaJobCenter: ObservableObject {
    @Published private(set) var jobs: [MediaJob] = []
    func enqueue(_ request: MediaJobRequest)   // dedupes, then queues
    func cancel(_ id: UUID)                    // SIGTERM → 2s → SIGKILL → rm partial
    func dismiss(_ id: UUID)                   // terminal cards only
    var hasLiveWork: Bool                      // feeds ActiveWorkGate
}

How progress actually arrives

ffmpeg is asked for a machine-readable progress stream on stdout, which is currently thrown away entirely. The change to the argument list is small; the change to what the user sees is not. 

// before — silent, unobservable
["-nostdin", "-loglevel", "error", "-y", "-i", input] + extra + [output]

// after — a key=value line block roughly twice a second on stdout
["-nostdin", "-loglevel", "error", "-y",
 "-progress", "pipe:1", "-nostats",
 "-i", input] + extra + [output]
// what ffmpeg then writes, and what MediaProgress.parse() turns into a MediaJob update
out_time_us=252480000
total_size=41582592
speed=1.83x
progress=continue

Duration comes from parsing ffmpeg's own Duration: 00:11:02.34 banner. If that fails we show an indeterminate bar with elapsed time and bytes written, and we do not invent a percentage.

Changed during implementation. The plan opened with an AVAsset fast path and fell back to the banner. Dropped: AVFoundation cannot open MKV or WebM at all, and it cannot answer the second half of the question — the source audio codec, which decides whether the track can be lifted out without re-encoding — without loading tracks anyway. One uniform probe that works for every container the app can download beat a fast path covering half of them.

Cards for finished jobs clear themselves after 12 seconds (8 in the original plan — raised so there is time to reach “Reveal in Finder” before the card goes). Cancelled cards clear on the same timer. Failed cards stay until dismissed — a failure you didn't read is a failure you didn't get told about. Past five cards the stack stops growing and the rest are summarised as “+N more waiting”, because this is an overlay on the window and cannot scroll.

Why a docked card and not a row in the main list

The main list is bound to DownloadTasks owned by the DownloadManager actor. A conversion is not a download: it has no URL, no bytes-per-second over a network, no resume, no retry, no persistence. Forcing it into that model would mean either a fake DownloadTask (which then leaks into History, the CLI, the portal API and every filter) or a variant enum that every list call site has to unwrap. The dock is additive: nothing that exists today changes shape.

Cut during implementation — the one thing in this mockup that is not in the build. The per-format size estimates are gone. Getting one needs the source duration, the duration needs an ffmpeg -i probe, and a probe is a process — this would have spawned one from inside a submenu the user may only be passing over, then cached the answer so that the first right-click on any file showed bare names anyway. The estimate still runs where it can actually act on the answer: the free-space pre-flight, which refuses the job before it starts if the disk cannot hold the result. The Convert To menu keeps its “copy, instant” label — that one is derived from the two file extensions alone, costs nothing, and is right the first time.

Behaviour spec

The decisions worth arguing about, stated explicitly so you can overrule any of them now rather than after the code exists.

Concurrency
2 simultaneous jobs, the rest queued and shown as “Waiting…”. ffmpeg already saturates all cores per job; a third concurrent transcode makes every job slower, not the batch faster. Configurable in Settings → Media tools if you want it.
Dedupe
Enqueueing an (input, target) pair that is already queued or running does not start a second job — it flashes the existing card instead.
Cancel
SIGTERM → 2-second grace → SIGKILL. The partial output is deleted and the card says “Partial file removed”, so a deletion is never silent — and it says “Nothing was written” instead when the job was cancelled before it ever claimed a file, because asserting a cleanup that did not happen is its own small lie. If a cancel is still outstanding after 6 seconds (a SIGKILL has landed and the process still hasn't exited — uninterruptible I/O on a stalled volume is the realistic case) the card turns amber, says so, and offers Stop waiting, which releases the queue slot and the card. A .cancelling job stops counting against the concurrency cap the moment it is asked to stop, so one wedged cancel can never wedge the queue behind it.
Stall detection
Replaces the blind 30-minute kill. If out_time hasn't advanced in 5 minutes, the card turns amber and offers Cancel — but does not kill. A slow-but-alive 4-hour transcode is no longer murdered at minute 30, and a genuinely wedged one is flagged 25 minutes earlier.
Quitting
Live media jobs set ActiveWorkGate.hasActiveWork, so Quit raises the existing confirmation. Confirming cancels each job cleanly (partials removed) rather than orphaning them.
Disk space
Estimate the output before launching; if free space is under estimate × 1.2, refuse the job with both numbers in the message rather than letting ffmpeg discover ENOSPC twenty minutes in. changed The estimate is not also shown in the menu — see the note under the context-menu mockups.
Notifications
Only for jobs that ran longer than 20 seconds — a notification for a 1.5-second stream copy you were watching is noise. Beyond that, conversions obey the same three notification settings as everything else in the app: notifyOnCompleted, notifyOnFailed, and notifyOnlyWhenInactive. changed The plan hardcoded “only when not frontmost”; that is the user's switch, not ours.
Accessibility
The dock is an .updatesFrequently live region; start and terminal states are announced, intermediate percentages are not (VoiceOver reading “39%… 40%…” forever is hostile).
Failure text
Full stderr retained on the job, shown in a scrollable box in the card, with Copy details. The one-line summary stays plain-language; the raw output is there when it's needed.
History
not shipped Finished conversions would be appended to the existing History view as a distinct kind. Listed here as lowest priority and droppable, and dropped: it means a new persisted record type touching the History store, the CLI and the portal API, for a feature whose actual complaint was “I can't see what's happening right now”. Worth doing on its own, not inside this change.

The stream-copy fix (gap #5)

This one is a genuine defect rather than missing UI, and it's the reason conversions feel so slow that the absent progress bar hurts as much as it does. 

// FFmpegService.convert — current
static func convert(input: URL, toExtension ext: String, …) async -> Outcome {
    let output = uniqueSibling(of: input, extension: ext)
    return await run(input: input, output: output,
                     extraArgs: [],        // ← no codec flags at all
                     override: override)
}

With no -c flags, ffmpeg picks each output stream's encoder from the container's defaults and re-encodes. Converting a 1080p H.264 MP4 to MKV — a pure container swap where every byte of the video stream could be copied verbatim — instead spends minutes re-compressing and throws away quality doing it.

Proposed

  • Attempt -c copy first for container changes. MP4→MKV, MKV→MP4, MOV→MP4 typically finish in seconds, losslessly.
  • If ffmpeg refuses (target container can't hold that codec — e.g. some MKV audio into MP4), fall back to a re-encode and say so on the card: “WebM can't store this audio track — re-encoding, this will take longer.”
  • Same for audio extraction: if the source audio codec already matches the target (AAC → M4A, FLAC → FLAC), use -c:a copy. Instant and bit-exact instead of a lossy re-encode of already-lossy audio.

Net effect: the most common conversions stop being slow at all, and the ones that genuinely are slow now explain why.

What gets tested

Following the pattern already set by MediaWorkflowTests: parsers are pure and live in Core, so the tests run on a CI box with no ffmpeg and still protect the real logic.

  • Progress-block parsing, including partial blocks split across pipe reads (the realistic failure mode).
  • Duration: banner parsing — present, absent, malformed, and streams reporting N/A.
  • Fraction never exceeds 1.0 when out_time overruns a slightly-wrong duration.
  • ETA arithmetic at 0% (no estimate offered rather than “∞”), mid-run, and at 100%.
  • Size estimation per audio format against known bitrates.
  • Stall detection: advancing vs static out_time across the threshold.
  • Dedupe key: same input + same target collides; same input + different target does not.
  • Codec-compatibility decision table for the copy-vs-re-encode choice.
